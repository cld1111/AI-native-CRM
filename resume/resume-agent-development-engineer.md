## 简历正文（可直接复制）

### AI Native CRM｜受控 Agent 执行与评测闭环

面向跨境商家的客户经营 CRM。销售要在 WhatsApp 客户会话、商机记录与飞书内部事实之间核对信息，并区分客户偏好、公司知识与商业承诺的授权来源。我独立设计了 Agent 的执行分层、协作拓扑、记忆权威与评测闭环：客户事实留在 SQL 持久账本，Agent 读取确认记忆与产品依据后协作分析商机，产出带来源的报告；对客动作保留独立审批，执行轨迹与分层评测用于定位事实遗漏、协作冲突和输出失败。

- **Agent 执行分层**：模型一次返回不等同于业务完成，把 Pi Agent Core 限定为模型/工具循环内核，业务 Harness 管理客户作用域与工具副作用分类，持久 Worker 承接 SQL 队列领取、租约检查与恢复；执行状态、动作待确认与任务终态在 Run/提案/账本独立留痕，使模型推理、业务授权与任务恢复可分开审查。

- **多 Agent 协作与冲突可解释**：商机评审需要多角度核对客户事实、跟进状态与公司政策，子专家限定为只读子运行并共享工具配额，父流程汇总并承接受控写入；用字段值 hash 与来源 revision 区分事实分歧、知识改版与互补片段，保留冲突位置，让报告可沿字段与版本追查分歧依据。

- **记忆权威与可降级读取**：跨会话延续客户偏好需要长期记忆，但外置服务故障不能让已确认事实被判不存在。人工确认事实以 SQL 为权威，外置 Mem0 仅作可选排序投影；远端命中核对归属标识与内容 hash 后只调整本地顺序，返回前重验隐私与最新事实；远端不可用时保留本地事实，不把"未检索到"误判为"客户没说过"。

- **工具效果分类与审批边界**：客户档案查询、可逆商机更新和对外发送属于不同风险等级，模型不能共享同一授权假设。工具按 read-only / 可逆 lead update / internal question / customer send 分层配置守卫，对外发送只走 approved_reply 的独立发送消费者；把"模型看见工具 ≠ 工具能直接执行"固定在效果层，不让模型自由拼接权限。

- **确定性先行 + 版本化语义 Judge**：报告引用真实记录仍可能把"在谈"写成"已成交"，Judge 高分不能附着于新材料。先在成功工具观察上做来源与字段断言的确定性核验，再运行独立语义 Judge；评测按材料与 rubric/model 指纹匹配，资料变化后拒绝旧评价，合并取更严格 verdict，使语义高分不能覆盖确定性失败。

## 边界与归因（不进简历）

- **归因范围**：Agent 执行、协作、记忆、观测与评测层为本人独立设计（2026-10-08 确认）；CRM 前端 UI、通用后端、部署不在归因范围内。
- **未触达边界**：普通 Workbench 外发未闭合；飞书仅接口代码级实现；Judge 分数为本机合成历史总评 needs_review，不是准确率。
- **数字约束**：不出现转化率、提效百分比等无原始测量依据的指标。
